# Discovery and route-quality audit, 2026-09-13

Read-only audit of current source. No production edits. Reproduction and raw functional evidence: `discovery-wiring.ts` and `discovery-wiring.json` in this directory. These are bounded operation-count probes, not timing benchmarks. Source paths below are relative to repository root.

## Confirmed findings

### P1: The advertised P1 A/B driver runs default tuning on both sides

`scripts/slurm-p1-benchmark.sh:49-60` sets `SOKOMIND_TUNING_JSON` and invokes `benchmark:solver:v2`. V2 does not parse that environment variable. `scripts/solver-v2-benchmark-lib.ts:450-460` creates `createNodeSolverAdapter()` with no options, and its tuning fingerprint at lines 382-383 resolves defaults. The adapter resolves only `options.tuning` (`src/solver/implementations/sokomind-solver.ts:371-372`). The only environment parser is in the separate older `scripts/benchmark-sokomind-solver.ts:130-137`.

The probe resolves each advertised treatment (walk weight 0.05, keeper arrival 1, intermediate quota 2). All actual values remain zero and all fingerprints remain `f9eec8cceb9a3ff1`. This is a wiring failure, not evidence that the changes have no effect. Conclusions in `docs/solver-benchmarks.md:465-473` attributed to these A/B runs cannot justify class-specific activation or rejection unless separate raw artifacts establish that the treatments actually reached the engine.

Fix the driver and harness together: pass explicit validated tuning into the adapter; record effective tuning per sample and child; distinguish control/treatment run identities; require intended parameter changes and nonzero mechanism counters before interpreting results. Prefer Sokomind discovery profiles for these experiments; the current script needlessly repeats exact profiles too. A malformed/ignored treatment should fail before launching the matrix.

### P2: Intermediate retention does not reach the main targeted macro path

`src/solver/implementations/sokomind-engine/source/solver-search.js:1966-1984` passes `macroIntermediateQuota` only to `expandPushSequences`, not `expandTargetedPushSequence`. Objectives derive from a doorway task or current assignment at lines 1898-1916. The targeted implementation in `source/push-generation.js:466-668` has no intermediate-quota handling. The untargeted implementation at lines 428-463 does.

Grand Hall's first structural layer with an explicit quota of eight makes eight targeted calls, zero untargeted calls, passes no quota to all eight calls, and returns zero tagged intermediate candidates. Visited/generated work is 1/18. Fixing only the benchmark environment therefore still leaves the main missing-handoff experiment untested. The documentation's claim that tagging supports beam dedup is also stronger than the code: `intermediateOf` is written at `push-generation.js:460` but not propagated into the child at `solver-search.js:2046-2054` or consumed elsewhere.

Implement a bounded targeted-intermediate control and first confirm generation and retention in a designed witness. Reserve at most one or two useful handoffs within the existing beam budget, selected by next-box support access/released obligation and actual move cost. Do not merely widen every beam or retain arbitrary short prefixes. Track macro-generated, macro-returned, post-transposition, and final-beam survival separately. Replay final routes and keep all controls disabled until generalization is established.

### P2: The schedule diagnosis command rejects its own encoded incumbent

`scripts/diagnose-schedule-trace.ts:93-96` converts solver directions to `U/D/L/R`, then passes them as the engine's `solutionPath` at lines 102-109. The legacy engine expects full names (`Up/Down/Left/Right`), as existing schedule-trace unit fixtures correctly use. `source/box-rescheduling.js:170-171` rejects the path before any repair work.

Reproduction: `node --experimental-strip-types scripts/diagnose-schedule-trace.ts --fixture=ultra-tiny` finds the one-move route then fails at line 113, `Rescheduling produced no path`. Probe evidence: `["Down"]` validates; `["D"]` yields `illegal-solution-path` and `invalid-rescheduling-incumbent`, visited zero. Also the command claims quality mode at line 81 but passes no mode at line 79; the actual default is fast (`sokomind-options.ts:23`). Use the shared direction translation and set/report the intended mode explicitly. Add a tiny command smoke check covering this actual boundary.

## Ranked improvement work

1. **Restore trustworthy experiment and diagnosis wiring first.** The existing documented negative P1 result is not a reliable basis for tuning decisions. Establish a narrow structural-lane control, explicit treatments, witness fixtures, and exercise/retention counters before paying for another corpus sweep.
2. **Recover useful handoffs before increasing move weights.** The current planner retains the ordinary one-push alternative only for the first two selected branches (`solver-search.js:2023-2026`), while targeted endpoint order is target distance, pushes, then moves (`push-generation.js:309-314`). A better outer score cannot recover candidates removed earlier. Use the existing offline `scripts/diagnose-planner-route.ts` recoverability observer with an independently replayed route as a diagnostic witness. Keep reference routes out of runtime payloads. Identify the first lost handoff and make one fixed-budget generation/retention change addressing it.
3. **Price the next feasible task on partial schedules, including keeper arrival.** The working repair model owns `(phase, box, robot)` and actual support distances (`source/box-rescheduling.js:40-78`). The partial planner currently chooses locally completed task endpoints using `path.length + 3 * relaxedPushDistance` (`source/strategic-planning.js:83-105`), then scores only `path.length + remainingPushes + structural penalties` (lines 289-294). Prototype a separate bounded lane carrying an explicit unresolved-task set and physically replayable candidate state. For each next enabled task, simulate the required support walk and push sequence; compare accumulated moves plus an optimistic remainder, and retain the cheapest next-task arrival as well as one complementary approach. Derive release/clearance candidates from the board and unresolved obligations. Fixed-order repair's future occupancy masks cannot be copied as known facts into an unfinished schedule. Any schedule-specific blocker evidence must stay scoped to that candidate/hypothesis. Existing defaults stay as recovery controls. This is a distinct costed-feasibility experiment, not another larger analysis budget or the previously rejected globally connected inference toggle.
4. **Add distance-only reachability access before activating keeper-aware scoring.** `keeperApproachProfile` (`solver-search.js:166-184`) constructs a full array with `reachable.get(support)` for every legal support merely to inspect `.length`. `reachablePaths` reconstructs and reverses each array by walking parent links (`source/analysis.js:690-698`); first-push scoring independently walks the same parent chains (`solver-search.js:1822-1824`). A bounded first-layer probe with explicit keeper-aware transpositions performs 17 profiles, allocates 671 path arrays, and copies 7,594 move entries for distance-only use (maximum support distance 32), with unchanged 1/18 layer work. Expose numeric BFS distances or a lazily memoized distance accessor and preserve existing parent-based path reconstruction for actual accepted moves. Count the added distance storage in cache memory accounting. This is an allocation-reduction hypothesis, not a measured speedup; compare exact ranks, routes, counters, estimated memory, and isolated timing before claiming a benefit.
5. **Preserve later-task alternatives at a fixed width in the partial scheduler.** Unless `scheduleChoices` is enabled, `strategic-planning.js:310-338` admits at most one continuation per first task. Exporting any candidate to `plan.candidates` collapses again to one candidate per first task at lines 347-350. Thus keeper/owner alternatives acquired deeper in a schedule can be discarded even with spare beam capacity. Replace spare-capacity filling with distinct board/keeper continuation retention as an independently switchable control; do not enable the whole previously failed schedule-choice feature. Use route recoverability and completion fraction to show which alternatives survive and whether they help.

## Limits

These probes establish defects and concrete operation counts, not improved full-route quality or browser speed. No full corpus or timing benchmark was run by this subtask. Grand Hall's first-layer task list had no boxes assigned to multiple room tasks, so a speculative last-task-per-box map concern was not retained as a finding. Production proof kernels and replay validation were outside this subtask; none of these incomplete discovery changes can establish move optimality.
